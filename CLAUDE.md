# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visão geral

Firmware para **ESP32-S3 Super Mini** (FH4R2: 4 MB flash quad + 2 MB PSRAM quad) que consome o stream **SSE** da API CertMind por **uma única conexão HTTP persistente** (GET, texto claro, sem TLS) e aciona os pixels de uma **barra WS2812 de 8 LEDs no GPIO 13** conforme cada situação emitida pelo backend. Desde a v3.2 (M3 do porte) a barra tem **dois canais independentes**: pixels **0–5 = respostas A–F / 1–6** (cores dos LEDs físicos do antigo D1 Mini + magenta para F) e pixels **6–7 = status dedicado** (6 = conexão: âmbar piscando/pulso violeta; 7 = processamento: ciano piscando). O servidor difunde **dois eventos**: `answer` (a resposta resolvida) e `status` (andamento do processamento: `solving`/`idle`/`error`). O ESP é apenas consumidor: abre o GET e escuta; não faz POST nem envia imagem. Projeto **PlatformIO**, ambiente único `[env:esp32s3_supermini]`. Desde a v3.3 o firmware é dual-core: `netTask` (core 0) para rede/parse e `loop()`/uiTask (core 1) para os LEDs, ligadas por uma fila de comandos por valor. O roteiro da migração (marcos M5–M7 restantes) está em `PLANO_MIGRACAO_ESP32S3.md`.

## Comandos

```bash
pio run                 # Compila o firmware
pio run --target upload # Compila e grava via USB-C (porta fixada em COM6 no platformio.ini)
pio device monitor      # Monitor serial (115200 baud, USB-CDC nativo)
pio run --target clean  # Limpa artefatos de build
```

Não há testes automatizados — é firmware embarcado validado em hardware via Serial Monitor. Para capturar o boot (que ocorre antes de o monitor abrir), force um reset com o monitor já conectado (pulso no RTS). O bootloader ROM do S3 **não fala pelo USB-CDC**: as primeiras linhas do ROM não aparecem, mas o log do firmware sai completo.

## Arquitetura

Modular, uma responsabilidade por arquivo:
- `src/Config.h` — todas as constantes via `#define` (WiFi, endpoint do stream, barra de LED, timings dos padrões, backoff, tetos de buffer). As cores `LED_COLOR_*` são hex cru (`0xRRGGBB`) de propósito, para o `Config.h` não depender do FastLED.
- `src/WiFiManager.{h,cpp}` — conexão WiFi inicial (modo STA) + helpers de status. Chama `WiFi.setSleep(false)` — obrigatório, ver gotchas.
- `src/SseClient.{h,cpp}` — abre o GET, valida headers, de-framing chunked, parser SSE não-bloqueante linha-a-linha, reconexão com backoff, timeout próprio por fase (headers × stream). Ao fim de um evento `answer` ou `status`, chama o callback correspondente com o payload; outros nomes de evento são descartados.
- `src/LedController.{h,cpp}` — máquina de estados da barra (6 respostas + 2 status), **toda em `millis()`** (zero `delay()` na renderização). A saída é um framebuffer `CRGB[8]` transmitido via FastLED/RMT; `flush()` só chama `FastLED.show()` quando o frame mudou.
- `src/main.cpp` — liga tudo e define o split dual-core: a **`netTask` (core 0)** roda WiFi + `sse.loop()` + parse (`handleAnswer()` decide por `hasData` + `questionType`, `handleStatus()` por `state`) e enfileira `LedCommand`; o **`loop()`/uiTask (core 1, tick 5 ms)** drena a fila e roda `leds.update()`.

Fluxo: `SseClient` (netTask) recebe `answer`/`status` → `handleAnswer()`/`handleStatus()` parseia e decide → fila de `LedCommand` (por valor) → `applyLedCommand()` na loopTask → `LedController` exibe.

## Pontos críticos (gotchas)

- **Invariantes do dual-core (v3.3) — a maior fonte potencial de bugs novos.** (1) A fila `g_ledQueue` carrega `LedCommand` **por valor**, com os dados já decodificados — **NUNCA** enfileirar um ponteiro para o payload (`_dataBuf` do `SseClient`): o buffer é reescrito no próximo evento e o consumidor leria lixo (use-after-write). (2) O `LedController` é tocado **exclusivamente** pela loopTask (`applyLedCommand()` + `leds.update()`) — nenhum código da netTask pode chamar `leds.*` diretamente; é isso que dispensa mutex no controller inteiro. (3) A saúde do stream (`LED_CMD_CONNECTED`) é enfileirada **só na transição**, não a cada iteração. A netTask pode bloquear à vontade (é o ponto do desenho: `connect()` TCP de ~5 s e `wifiManager.connect()` de 15 s não congelam mais a animação).
- **Parsing JSON é zero-copy — NÃO mude o callback para `const char*`.** `SseClient::AnswerCallback` é `void(*)(char*)` e `handleAnswer(char* payload)` passa o buffer **mutável** (`_dataBuf`) a `deserializeJson`. Isso ativa o `StringMover` do ArduinoJson (strings *Linked*, sem cópia: o pool carrega só a estrutura). Se voltar a `const char*`, o ArduinoJson copia as strings para o pool e um payload verboso pode **estourar** o `StaticJsonDocument<JSON_DOC_SIZE>` → `NoMemory` → LEDs não acendem. Foi o bug corrigido na v2.1 (na época com 512 bytes de pool; hoje são 4096, mas o contrato continua obrigatório — sem zero-copy as strings passam a competir pelo pool de novo). As strings extraídas (ex.: `answerText` para log) só são válidas **dentro** de `handleAnswer`, pois o buffer é reescrito no próximo evento; o que precisar sobreviver deve ser copiado (`strlcpy`).
- **Sem filtro do ArduinoJson desde a v3.1 (M2).** O filtro só existia para ignorar `explanation` e caber nos 512 bytes do 8266; com `JSON_DOC_SIZE` 4096 o documento vê o payload inteiro. O uso do pool é logado a cada `answer` (`[JSON] pool=`) — é o indicador de quando o teto precisar crescer.
- **`yield()` → `delay(1)` é intencional — NÃO reverter.** Sob FreeRTOS (ESP32), `yield()` vira `vPortYield()` e **não** alimenta o WDT nem cede o tick; `delay(1)` faz as duas coisas. Há dois pontos: fim do `loop()` em `main.cpp` e entre linhas do parser em `SseClient.cpp` (`feedLine`). Eram `yield()` no ESP8266.
- **`WiFi.setSleep(false)` é obrigatório** (`WiFiManager::connect()`): o modem sleep do ESP32 vem ligado por padrão e injeta dezenas a centenas de ms de jitter na recepção — inaceitável num stream cuja latência é o ponto do projeto.
- **`FastLED.show()` só quando o frame muda.** `writeMask()` (pixels de resposta, cache `_lastMask`) e `setStatusPixel()` (pixels 6–7, comparação com o valor corrente) apenas marcam `_dirty`; `flush()` no fim de `update()` transmite uma única vez, e só se algo mudou — `update()` roda a cada iteração do loop e um `show()` incondicional seria refresh contínuo desperdiçado. O sentinel `_lastMask = 0xFF` força a 1ª transmissão.
- **Evento `status` = canal de processamento (pixel 7, desde a v3.2).** `solving` → `showProcessing()` seta `_processing` e o **pixel 7 pisca ciano** a `LED_PROC_BLINK_MS` **sem TTL**, até chegar `answer`/`error`/`idle` — **sem tocar na resposta em exibição** (antes da v3.2, quando status e resposta dividiam os mesmos 5 LEDs, o solving vencia a resposta segurada e o `stopProcessing()` precisava ser condicional; com canais separados essa cicatriz da v2.4 se dissolveu). `error` → `showError()` (nos pixels de resposta). `idle`/`state` desconhecido → `stopProcessing()` (spec). Como o processando não tem TTL, `setConnected(false)` **aborta** `_processing` — senão o pixel 7 piscaria para sempre escondendo a queda do stream; ao reabrir, o `status` inicial do servidor ressincroniza. Erro de parse do `status` **não** aciona `showError()` (ao contrário do `answer`): o padrão de erro é reservado às respostas, e piscar os 6 aqui seria lido como "questão ilegível" — fica só no log `[JSON]`.
- **`LedController` é não-bloqueante; resposta e status são canais independentes.** `single`/`multiple`/`yesno` ficam em **HOLD por `LED_HOLD_TTL_MS`** (12 s) e então apagam; um novo `answer` sempre interrompe. `test`/erro/sequências (`dropdown`/`ordering`/`matching`) **tocam e apagam**. Toda exibição HOLD começa com um **blank de `LED_HOLD_INTAKE_MS`** (~250 ms tudo apagado) para tornar visível a chegada de respostas **iguais consecutivas** (ex.: `A` depois `A`) — sem ele, dois answers idênticos seriam indistinguíveis. O `renderHold()` usa `_animStart` p/ o TTL/blank e mantém duas máscaras (`_holdMask` fixo + `_holdBlinkMask` piscando); no `yesno` cada afirmação acende seu pixel simultaneamente (**Sim = fixo, Não = piscando**, `LED_YESNO_BLINK_MS`), e `single`/`multiple` zeram a de piscar (estáticos). A conexão é sinalizada **sempre** no pixel 6 (`renderStatus()`): âmbar piscando = conectando/reconectando; pulso violeta curto = ocioso (cor exclusiva de status — nenhuma cor de status pode coincidir com uma cor de resposta).
- **Janela de boot (v2.2).** Após `begin()`, a barra sinaliza normalmente por `LED_BOOT_BLINK_MS` (5 min); depois entra em **blackout total** (respostas **e** status apagados, gate no início de `update()`) **até a 1ª resposta**. O SSE e os logs na serial **seguem ativos** no blackout — só a saída dos LEDs é suprimida. Qualquer evento `answer` (single/multiple/yesno/sequência/`test`/erro) **ou um `status: solving`** marca `_firstAnswerReceived = true` (setado nos cinco pontos: `startHold`/`startSeq`/`showTestChase`/`showError`/`showProcessing`) e **encerra o blackout em definitivo** — ele não rearma. Se a 1ª resposta chegar antes dos 5 min, o blackout nunca ocorre. (`_answerActive` implica `_firstAnswerReceived`, então o gate nunca interfere na exibição de uma resposta.)
- **Erro de parse aciona `leds.showError()`** (não falha em silêncio) — o `return` silencioso era o que escondia bugs como o da v2.1.
- **O corpo do SSE vem em `Transfer-Encoding: chunked` e o `SseClient` desmonta os frames (v2.3) — não remover essa camada.** O backend (Kestrel) prefixa cada bloco com o tamanho em hex e o sufixa com CRLF, então o que chega na conexão **não** é o corpo lógico. `feedChunkedByte()` consome size/CRLF e passa a `feedLine()` só os bytes de dados; `beginChunkSize()` rearma o de-framing em `begin()`/`tryConnect()`/`closeConnection()` e ao entrar em `ST_STREAMING`. Sem isso, o CRLF terminador de um chunk que caia **no meio de uma linha `data:`** corta a linha ali → payload truncado → `showError()`; funcionava por acidente porque o Kestrel costuma emitir 1 chunk por evento. Uma linha de chunk-size **sem nenhum dígito hex** é ruído/trailer e só rearma (tratá-la como tamanho 0 dispararia um retry extra e pularia um degrau do backoff). O caminho identity (servidor sem chunked) segue funcionando: `_chunked` é detectado nos headers.
- **Timeout por fase (v2.5).** `ST_HEADERS` tem teto próprio (`HEADERS_TIMEOUT_MS`, 10 s): num half-open (servidor aceita o TCP e nunca responde, sem FIN), `_client.connected()` segue `true` e sem esse teto o firmware ficava **preso para sempre** em "conectando". O status HTTP é extraído numericamente (`atoi` após o 1º espaço) — a reason-phrase é opcional na RFC 7230 e um `HTTP/1.1 200` seco era rejeitado.
- **Todo header de resposta é logado (`[SSE] < ...`)** — não reduzir de volta a "só a linha de status". Foi justamente a ausência desse log que manteve a falta do de-framing chunked invisível.
- **Sem TLS**: usa `WiFiClient` puro e monta o GET manualmente. Não reintroduzir `HTTPClient` (bloqueia esperando o corpo terminar, incompatível com stream infinito) nem `WiFiClientSecure` (o backend não tem HTTPS; TLS é o M7 do plano, bloqueado pelo backend).

## Configuração

Toda parametrização fica em **`src/Config.h`**. Em dev local, trocar `STREAM_HOST`/`STREAM_PORT`/`STREAM_PATH`. O `monitor_speed` em `platformio.ini` deve bater com `SERIAL_BAUD_RATE` (115200). O teto de potência da barra (`LED_MAX_MILLIAMPS`, 600 mA) protege a porta USB — não subir sem fonte externa.

## Restrições

- **NÃO alterar as credenciais WiFi em `src/Config.h`** — ficam versionadas em texto plano por decisão do mantenedor; manter como estão.
- O rádio do ESP32-S3 só opera em WiFi **2,4 GHz**.
- **ArduinoJson fica na v6** (6.21.x) até o fim do porte — a v7 troca documentos estáticos por alocação dinâmica; mudar de major junto com a plataforma seria variável a mais.
